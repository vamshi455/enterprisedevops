The gates

GATE 0 · FEATURE TEST

Tested before the PR

Each feature branch gets its own config DB: a copy of DEV plus the branch’s DACPAC and config scripts. ADF is debugged against it in Git mode.

feature-env.yml · sqldb-etlcfg-ft-<story>
GATE 1 · PR → MAIN

Reviewed, traceable, tested

Linked story, tech lead approval, build green including the DACPAC, feature-test run id in the PR, comments resolved, squash merge only.

Azure Repos branch policies
GATE 2 · RELEASE CUT

Only the chosen PRs

Each PR merged, linked, not yet in prod. Ordered by merge time, cherry-picked onto the last prod tag. Missing predecessors are named.

build_release.py
GATE 3 · QA

QA lead accepts the drop

Same artifact that will reach prod. A failed story is dropped by re-cutting without its PR.

Environment shell-data-qa
GATE 4 · UAT

QA sign-off recorded

Business users test in UAT; their sign-off is attached to the change request.

Environment shell-data-uat
GATE 5 · CHANGE REQUEST

CR approved, PRs match

Approved, Scheduled or Implement, inside the change window, and the CR's Release-PRs line equals the manifest.

cr_gate.py · ServiceNow
GATE 6 · PROD

Release manager go

Deploy Azure SQL config, then UC SQL, then Databricks bundle, then ADF. Tag prod/<id>, close the CR, close the stories.

Environment shell-data-prod
  • Test on the feature branch, not after merge. Config scripts and ADF changes are tested together against the branch’s own config DB.
  • Config travels with its PR. One MERGE file per config key, deployed with the PR that needs it, to every environment.
  • One PR = one squash commit = one story. That is what makes a PR safe to cherry-pick.
  • main feeds DEV only. QA, UAT and PROD get release/<id>.
  • Build once, deploy many. What QA tested is byte-for-byte what reaches production.
  • The prod baseline is a tag. The next release starts from prod/<last>, so only your PRs move.
